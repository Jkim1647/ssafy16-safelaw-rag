# 검색 파이프라인 트러블슈팅

이 문서는 SafeLaw의 법령 검색 파이프라인을 구현하고 평가하면서 확인한 문제를 `현상 → 원인 → 시도 → 결과 → 해결` 순서로 기록한다. 단순 성공 결과뿐 아니라 성능이 나빠진 시도도 남겨 같은 문제를 반복하지 않도록 한다.

## 먼저 알아둘 검색 지표

### RRF

RRF(Reciprocal Rank Fusion)는 여러 검색 결과의 **순위**를 하나로 합치는 방법이다. 벡터 거리처럼 검색 방식마다 범위가 다른 원점수를 직접 더하지 않고, 각 결과에서 몇 위였는지를 사용한다.

```text
RRF 점수(문서 d) = Σ 검색별 가중치 / (k + 해당 검색에서 d의 순위)
```

현재 구현은 `k=60`을 사용한다. 예를 들어 같은 조문이 원문 검색 2위, 재작성 검색 1위이고 가중치가 각각 0.7, 1.3이라면 다음 점수를 얻는다.

```text
0.7 / (60 + 2) + 1.3 / (60 + 1) ≈ 0.0326
```

여러 검색에서 꾸준히 상위에 등장한 조문이 최종 결과에서도 높아지는 것이 장점이다. 다만 현재 SafeLaw는 순수 RRF만 사용하지 않는다. 원문·재작성 질문에는 가중 RRF를 적용하고, 개별 법률 용어는 후보 수집에 사용한 뒤 가장 강한 용어 점수와 조문 제목 일치도를 반영하는 혼합 재정렬 방식이다.

### MRR

MRR(Mean Reciprocal Rank)은 각 질문에서 **첫 번째 정답이 몇 위에 나왔는지** 평가하는 지표다.

```text
질문별 RR = 1 / 첫 정답 순위
MRR = 모든 질문 RR의 평균
```

| 첫 정답 순위 | 질문별 RR |
|---:|---:|
| 1위 | 1.000 |
| 2위 | 0.500 |
| 3위 | 0.333 |
| 4위 | 0.250 |
| 5위 | 0.200 |
| Top-5 밖 | 0.000 |

예를 들어 세 질문의 첫 정답이 각각 1위, 2위, Top-5 밖이라면 MRR은 `(1 + 0.5 + 0) / 3 = 0.5`다. SafeLaw의 최종 MRR `0.747`은 30개 질문에서 정답이 모두 Top-5 안에 있었고, 다수가 1위였지만 일부는 2~4위였다는 뜻이다. MRR은 승소 가능성이나 답변 정확도가 아니라 **검색 순위 품질**만 나타낸다.

### Recall@5와 MRR을 같이 보는 이유

- Recall@5는 필요한 근거를 Top-5 안에서 **놓치지 않았는지** 본다.
- MRR은 찾은 근거를 사용자가 보기 쉬운 **앞 순위에 배치했는지** 본다.

따라서 Recall@5만 높고 MRR이 낮으면 정답 후보는 찾았지만 불필요한 조문 뒤에 묻혀 있을 수 있다.

## 1. 일상 표현으로 관련 조문을 찾지 못함

**현상**

- `해고 서면 통지`는 근로기준법 제27조가 1위였다.
- `회사에서 카카오톡으로 내일부터 나오지 말라고 했어요`는 같은 의미인데도 제27조가 Top-5에 없었다.

**원인**

사용자 표현인 `카카오톡`, `나오지 말라`와 법령 표현인 `해고`, `서면통지`, `해고의 효력` 사이에 어휘 차이가 있었다. 임베딩 검색만으로 이 차이를 항상 해결할 수는 없었다.

**해결**

개인정보를 먼저 마스킹한 뒤 규칙과 GMS LLM으로 법률 검색어를 만든다. 원문 질문도 함께 검색해 잘못된 확장어 하나에 전체 검색이 의존하지 않게 했다.

```text
카톡으로 내일부터 나오지 말래요
→ 해고, 해고 통보, 서면통지, 해고사유, 해고시기, 해고 효력
```

## 2. 법률 용어를 하나의 긴 문장으로 합치면 의미가 희석됨

**현상**

검색어 확장 후에도 일부 정확한 조문이 검색 상위에 나타나지 않았다.

**원인**

여러 법률 용어를 한 문자열로 합쳐 한 번만 임베딩하면 서로 다른 쟁점이 하나의 벡터에 섞인다. `임차권등기명령`처럼 강한 단일 신호도 일반적인 `보증금 반환`, `대항력` 등에 희석될 수 있었다.

**시도와 해결**

원문, 재작성 질문, 각 법률 용어를 별도 질의로 검색해 후보군을 넓혔다. 이 변경으로 전체 Recall@5는 `0.633 → 0.700`으로 올랐다.

## 3. 후보를 늘렸지만 MRR이 오히려 하락함

**현상**

개별 법률 용어를 모두 RRF에 더하자 Recall@5는 `0.633 → 0.700`으로 개선됐지만 MRR은 `0.525 → 0.411`로 하락했다.

**원인**

`임금`, `재산`, `등기`처럼 범위가 넓은 용어가 여러 조문에 반복해서 점수를 주었다. 관련 후보를 찾는 능력은 좋아졌지만 일반적인 조문이 정답보다 위에 배치됐다.

**해결**

- 원문과 재작성 질문만 가중 RRF로 누적한다.
- 개별 법률 용어는 문서마다 가장 높은 검색 점수 하나만 반영한다.
- 법률 용어와 조문 제목이 정확히 또는 부분적으로 일치할 때 재정렬 가점을 준다.

최종적으로 전체 Recall@5는 `1.000`, MRR은 `0.747`이 됐다. 후보 생성과 최종 순위 결정을 분리해야 한다는 점을 확인했다.

## 4. `전세보증금` 질문이 민법상 전세권 조문으로 치우침

**현상**

`살던 집이 경매로 넘어가면 제 전세보증금을 다른 채권자보다 먼저 받을 수 있나요?`에서 기대 조문인 주택임대차보호법 제3조의2가 누락되고 민법의 전세권 조문이 상위 5개를 차지했다.

**원인**

일상어 `전세`는 주택 임대차 보증금을 뜻하는 경우가 많지만, 법률 용어 `전세권`은 등기되는 별도의 물권이다. LLM이 질문을 `전세권`, `경매` 중심으로 확장해 다른 법률 개념으로 검색 범위를 좁혔다.

**해결**

주택 임대차 도메인에서 `경매·공매·채권자`와 `먼저·우선·배당·보증금`이 함께 등장하면 `보증금의 회수`, `우선변제권`을 추가한다. 조문 제목과 일치하는 `보증금의 회수`가 재정렬에 반영되면서 제3조의2가 1위로 검색됐다. 해당 표현은 회귀 테스트로 고정했다.

## 5. GMS 채팅 요청에서 HTTP 400 발생

**현상**

GMS의 `gpt-5-nano` 채팅 호출에 `temperature`를 포함했을 때 HTTP 400 응답이 발생했다.

**원인**

사용 중인 모델·호환 API 조합에서 해당 매개변수를 지원하지 않았다.

**해결**

필수 필드인 모델과 메시지만 보내도록 어댑터를 수정했다. API 키는 객체 표현, 예외 메시지, 결과 파일에 포함하지 않는다.

## 6. Chroma 색인은 일반 텍스트처럼 확인하기 어려움

**현상**

`data/indexes/`가 파일 탐색기에는 보이지만 에디터에서 내용을 바로 읽기 어렵고, 내부 파일을 열어도 저장된 벡터의 의미를 확인하기 힘들었다.

**원인**

Chroma는 JSON 문서 모음이 아니라 SQLite와 내부 바이너리 구조로 벡터·메타데이터를 관리한다. 또한 색인은 재생성 가능한 로컬 산출물이므로 Git에서 제외한다.

**해결**

내부 파일을 직접 수정하지 않고 `scripts/search_statutes.py`로 검색 결과와 메타데이터를 확인한다. 색인이 의심되면 조문·청크 수, 임베딩 모델, 벡터 차원을 manifest 및 자동화 테스트와 비교한다.

## 7. LLM 기반 평가 결과의 재현성 관리

**현상**

같은 질문이어도 LLM이 만드는 검색어가 조금씩 달라져 순위가 변할 수 있고, 긴 평가 중 외부 호출 실패가 발생할 수 있다.

**해결**

- 질문과 기대 조문을 30개 고정 평가셋으로 버전 관리한다.
- 각 문항이 끝날 때 결과를 원자적으로 저장하고 중단 시 이어서 실행한다.
- 검색 로직이 바뀌면 평가기 버전을 올려 이전 캐시를 재사용하지 않는다.
- 개선 전 기준선과 최종 결과를 별도 JSON으로 보존한다.
- 결과 해석 시 모델 변동과 자체 라벨 편향을 한계로 명시한다.

## 8. 근거는 맞지만 LLM의 JSON 문법이 깨짐

**현상**

실제 GMS 답변에서 올바른 근로기준법 문구와 근거 번호를 선택했지만 `summary` 객체 뒤에 불필요한 닫는 대괄호가 추가되어 JSON 파싱에 실패했다. 파이프라인은 이 응답을 `invalid_citations`로 차단했다.

**판단**

깨진 JSON을 정규식으로 임의 복구하면 필드 경계나 근거 연결을 잘못 해석할 수 있다. 법률 안내에서는 일부 내용을 추정 복구하는 것보다 답변을 폐기하는 편이 안전하다.

**해결**

- 첫 응답은 사용자에게 노출하지 않고 폐기한다.
- 같은 검색 근거로 JSON 형식 재생성을 한 번만 요청한다.
- 재생성한 응답도 처음부터 전체 인용 검증을 수행한다.
- 두 번째도 실패하면 고정된 차단 메시지만 표시한다.

실제 재실행에서 정상 질문은 `answered`, 법률과 무관한 점심 메뉴 질문은 `insufficient_evidence`로 처리되는 것을 확인했다.

## 판례 본문검색의 주변적 일치 문서 혼입

- 증상: `부당해고`, `상속` 등 넓은 단어로 수집하면 핵심 쟁점은 형사·세무인데 본문에서 해당 단어를 한 번 언급한 판례가 포함됐다.
- 원인: 국가법령정보 판례 목록의 `search=2`는 본문검색이라 검색어가 사건의 핵심 쟁점인지 보장하지 않는다.
- 해결: 검색 결과를 바로 저장하지 않고 검색어의 핵심 단어가 판시사항·판결요지·참조조문에 모두 있는지 검사했다. 동일 카테고리의 같은 사건번호도 하나만 남겼다.
- 남은 한계: 판결요지가 없는 판례는 원문을 대체 텍스트로 사용하므로 주변적 일치를 완전히 제거하지 못한다. 판례 평가셋을 만든 뒤 오탐 사례를 소스 설정과 재순위화 규칙에 반영해야 한다.
