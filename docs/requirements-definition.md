# 요구사항 정의서 — SafeLaw

> AI 코어 프로젝트 2회차 「RAG 기반 도메인 지식 서비스」 · 광주 3반 · 주제명 **SafeLaw (개인정보 보호형 생활법률 판례 내비게이터)**
>
> 이 문서는 명세서의 요구사항 예시(F2001~F2016, NF2001~NF2007)를 SafeLaw 도메인에 맞게 표현을 바꾸어 정의한다. 필수 기능의 의미는 바꾸지 않았다. 구현 여부와 증빙은 [`verification-results.md`](verification-results.md)의 요구사항 대조표에 기록한다.

## 1. 서비스 개요

사용자가 근로·임대차·상속 상황을 자연어로 적으면, 개인정보를 로컬에서 먼저 가린 뒤 관련 **법령 조문**과 **공개 판례**를 검색하고, 검색된 원문으로 검증되는 내용만 근거 번호와 함께 안내한다. 승소·패소를 예측하거나 법률 자문을 제공하지 않는다.

| 명세서 개념 | SafeLaw에서의 대응 |
|---|---|
| 항목(예: 영화 1편) | 법령 조문 1개 (예: 근로기준법 제27조) |
| 항목 메타데이터 RAG 1 | 법령 조문 컬렉션 `safelaw_statutes` |
| 외부 문서 RAG 2 | 공개 판례 컬렉션 `safelaw_cases` (사전 수집 + 질문 시 증분 수집) |
| 외부 문서 출처(위키백과) | 국가법령정보 공동활용 판례 목록·본문 API |
| 항목 선택 + 채팅 | 조문 선택 + 조문별 채팅 (`📚 조문 찾아보기`), 이어지는 상담 채팅 (`💬 상담실`) |
| 도메인 특화 기능 | 내 상황 쟁점 체크리스트 |

## 2. 도메인 확정과 선택 조건 충족 근거

| 조건 | 충족 근거 |
|---|---|
| 항목 메타데이터 약 100건 이상 | 국가법령정보 현행법령 API로 수집한 **381개 조문** (근로계약·부당해고 158, 전세·임대차 96, 상속 127). 조문마다 법령명·조문 번호·제목·시행일·공포일·소관부처·공식 원문 URL·쟁점 태그를 가진다. 본문이 "삭제"뿐인 4개 조문을 뺀 377개 조문을 382개 청크로 색인했다. |
| 항목마다 연결되는 외부 문서 | 국가법령정보 판례 목록·본문 API의 공개 판례. 기본 50건(노동 12, 임대차 27, 상속 11)을 652개 청크로 색인하고, 질문 시 부족한 판례를 추가 수집한다. 판례는 참조조문으로 법령 조문과 연결된다. |
| 출처와 이용 조건 기록 | API 주소·파라미터·인증 방식·수집 범위·건수·해시·이용 조건을 [`data-source-inventory.md`](data-source-inventory.md)에 기록했다. 국가법령정보센터는 제공 정보를 참고자료로 쓰도록 안내하며 법적 효력은 관보 등 공식 자료에 있다. |
| 근거 없이 답하면 틀리거나 위험한 질문 3개 이상 | 아래 질문 목록 참고 |
| 위험 도메인 여부와 면책 | 법률 판단은 잘못 안내하면 권리 행사 기한을 놓치는 등 피해가 생기는 **위험 도메인**이다. 모든 답변과 화면 하단에 "법률 자문이나 승소 가능성 예측이 아니다"라는 면책 문구를 표시하고, 판례를 인용하면 법령 개정·후속 판례를 함께 확인하라는 경고를 붙인다. |

근거가 필요한 질문 예시:

1. **"돌아가신 형이 전 재산을 지인에게 줬어요. 동생인 제가 유류분을 청구할 수 있나요?"** — 민법 제1112조는 2024.9.20 개정으로 형제자매의 유류분(제4호)이 삭제됐다. 개정 전 지식으로 답하면 "법정상속분의 3분의 1"이라고 틀리게 안내할 수 있다.
2. **"회사에서 카카오톡으로 내일부터 나오지 말라고 했어요. 이런 해고도 효력이 있나요?"** — 근로기준법 제27조의 서면통지 요건과, 카카오톡 공지를 서면통지로 볼 수 없다고 한 판례(서울고법 2022누56601)를 근거로 봐야 한다.
3. **"부모님 빚이 재산보다 많아요. 상속포기는 언제까지 해야 하나요?"** — 민법 제1019조의 3개월 기간과, 중대한 과실 없이 몰랐을 때의 특별한정승인(제3항)을 구분해야 한다. 기간을 틀리게 안내하면 회복이 어렵다.
4. **"퇴사했는데 마지막 월급을 다음 달에 주겠다고 해요."** — 근로기준법 제36조의 14일 금품 청산 기한과 합의 연장 예외를 정확히 인용해야 한다.

제공 도메인(영화)은 사용하지 않았다.

## 3. 기능적 요구사항

우선순위 `필수`는 명세서의 필수 기능이며 수정 없이 구현해야 한다. 표현만 SafeLaw에 맞게 바꿨다.

| 번호 | 분류 | 요구사항명 | 요구사항 상세 (SafeLaw) | 우선순위 |
|---|---|---|---|---|
| F2001 | 데이터 | 항목 메타데이터 적재 | 3개 분야의 법령 조문 381건을 로드하고, 조문 1건을 도메인·법령명·조문 번호·제목·쟁점 태그·본문이 이어진 하나의 색인 텍스트로 구성한다. | 필수 |
| F2002 | 색인 | 메타데이터 색인(RAG 1) | 조문 텍스트를 임베딩해 `safelaw_statutes` 컬렉션에 색인한다. 청크 ID를 `분야:법령조문ID:순번`으로 고정해 다시 색인해도 중복 저장되지 않는다. | 필수 |
| F2003 | 프롬프트 | 검색어 추출(프롬프트1) | 생활법률 검색어 변환기 역할 프롬프트로 마스킹된 질문에서 법률 검색 문장과 법률 용어를 JSON으로 추출한다. 선택한 조문이 있으면 그 조문을 질문 앞에 밝혀 항상 검색 대상에 포함한다. | 필수 |
| F2004 | 수집 | 외부 문서 수집(프롬프트2) | 법률 용어로 판례 목록 API를 검색하고, 선별 프롬프트가 사건번호·사건명·법원·선고일만 보고 본문을 받을 판례를 고른다. 선택된 판례만 본문과 공식 원문 URL을 수집하고, 이미 수집한 검색 계획은 다시 수집하지 않는다. | 필수 |
| F2005 | 색인 | 외부 문서 색인(RAG 2) | 수집한 판례를 쟁점·판단·주문·사실관계 섹션으로 나눠 청킹하고 `safelaw_cases` 컬렉션에 별도 색인한다. 청크 크기와 중복 길이는 `.env`로 조정한다. | 필수 |
| F2006 | 검색 | 근거 검색 및 병합 | 두 컬렉션을 각각 검색해 근거 번호로 병합하고, 같은 조문 청크와 같은 사건번호 판례를 중복 제거한다. 선택한 조문은 항상 근거에 포함한다. Top-k는 `.env`로 조정한다. | 필수 |
| F2007 | 생성 | 근거 기반 답변 생성(프롬프트3) | LangGraph `retrieve`·`generate` 두 노드로 구성하고, 검색된 법령·판례만 근거로 답한다. 근거에 법령/판례 유형을 구분하고, 근거가 없으면 답변하지 않고 확인되지 않는다고 안내한다. | 필수 |
| F2008 | 생성 | 근거 표시 | 주요 주장마다 `[근거 N]`을 붙이고, 실제 인용된 근거만 제목과 공식 원문 링크로 표시한다. 인용이 없거나 검증에 실패하면 답변 대신 그 사실을 안내한다. | 필수 |
| F2009 | UI | 항목 선택 및 질의응답 | 조건 탐색 카드 또는 분야별 전체 조문 목록에서 조문을 선택하고, 조문별로 분리된 대화 기록으로 채팅한다. | 필수 |
| F2010 | 서비스 | 도메인 특화 기능 | **내 상황 쟁점 체크리스트**: 검색된 근거가 요구하는 판단 요소를 뽑아 상황에 나와 있는지 표시하고, 확인 질문과 근거 번호를 함께 제시한다. | 필수 |
| F2011 | 서비스 | 조건 기반 항목 탐색 | 자연어 조건으로 법령 색인에서 후보 조문을 찾고, LLM이 조건에 맞는 조문만 골라 카드로 제시한다. 카드를 누르면 그 조문의 채팅으로 이어진다. | 필수 |
| F2012 | UI | 진행 상태 및 안내 | 검색·생성 중 진행 상태를 표시하고, 색인 없음·API 키 누락·근거 부족 안내와 법률 면책 문구를 표시한다. | 필수 |
| F2013 | UI | 프론트엔드 직접 구현 | HTML, CSS, JavaScript로 화면을 구현하고 서버와 요청·응답 형식을 분리한다. | 심화 |
| F2014 | 검색 | MMR 검색 적용 | 후보를 넉넉히 가져와 다양성 기준으로 근거를 고르고 유사도 검색과 비교한다. | 심화 |
| F2015 | 품질 | RAG 전후 품질 비교 | 대표 질문의 RAG 미사용·사용 답변을 나란히 두고 사실 정확성·근거 제시·모름 표시를 비교한다. | 심화 |
| F2016 | 수집 | 여러 문서 출처 결합 | 종류가 다른 문서(법령 조문, 판례)를 함께 색인하고 근거에 출처 종류를 구분한다. | 심화 |

### SafeLaw 추가 요구사항

| 번호 | 분류 | 요구사항명 | 요구사항 상세 |
|---|---|---|---|
| S01 | 보안 | 로컬 개인정보 마스킹 | 이름·주민등록번호·전화번호·이메일·주소·계좌번호와 사용자가 지정한 단어를 외부 호출 전에 플레이스홀더로 바꾼다. 원문과 치환 매핑은 저장하지 않는다. |
| S02 | 품질 | 인용 원문 검증 | 답변·체크리스트의 인용 문구가 검색 원문에 글자 그대로 있는지, 언급한 조문 번호가 인용 근거와 일치하는지 코드로 검증한다. |
| S03 | 검색 | 판례 권위 등급 | 전원합의체·대법원·항소심·기타 등급을 저장하고, 관련성이 비슷한 후보 사이에서만 상급심에 작은 가점을 준다. |
| S04 | 품질 | 평가셋 | 법령 30문항·판례 30문항·End-to-End 30문항으로 Recall@5·MRR·인용 정확성·거부 정확성을 측정한다. |

## 4. 비기능적 요구사항

| 번호 | 분류 | 요구사항명 | 요구사항 상세 (SafeLaw) |
|---|---|---|---|
| NF2001 | 성능 | 응답 시간 | 대표 질문의 검색·생성 전체 처리 시간을 측정해 기록한다. |
| NF2002 | 성능 | 수집 캐시 | 같은 마스킹 질문의 판례 수집은 SHA-256 캐시로 다시 호출하지 않고, 이미 가진 사건번호는 본문을 받지 않는다. |
| NF2003 | 보안 | API 키 관리 | `GMS_KEY`, `LAW_API_OC`는 `.env`로만 관리하고 Git·로그·데이터셋에 남기지 않는다. |
| NF2004 | 보안 | 내부 정보 비노출 | 화면에 API 키, 프롬프트 전문, 오류 추적 정보를 노출하지 않고 고정 안내 문구만 표시한다. |
| NF2005 | 확장성 | 모듈 분리 | 수집(`collectors`)·색인(`rag/indexing`, `adapters`)·검색(`rag/retrieval`)·생성(`rag/pipeline`)·UI(`ui`) 책임을 분리하고, 도메인에 묶인 수집 범위는 `data/*_sources.json`에 둔다. |
| NF2006 | 품질 | 외부 API 예절 | 재시도·호출 간격을 지키고 `User-Agent`에 서비스 식별 정보를 넣는다. |
| NF2007 | 법·윤리 | 출처와 이용 조건 | 수집 데이터의 출처·이용 조건·생성일·해시를 기록하고 공개 판례만 색인한다. |

## 5. 제공하지 않는 기능

- 승소·패소 확률 예측과 변호사를 대체하는 법률 자문
- 사용자 상담 원문의 파일·로그·Vector DB 저장
- 비공개 판결문이나 개인이 게시한 판결문 수집
