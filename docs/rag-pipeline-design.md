# RAG 파이프라인 설계문서 — SafeLaw

이 문서는 명세서 6장 「RAG 파이프라인 설계문서」 항목 순서대로 SafeLaw의 설계를 설명한다. 계층 구조와 보안 경계는 [`architecture.md`](architecture.md), 평가 수치는 [`verification-results.md`](verification-results.md)에 있다.

![SafeLaw 전체 아키텍처](assets/safelaw-hd-system-architecture.png)

## 1. 전체 흐름

```text
[오프라인]  법령 API → 조문 정규화 → 조문 구조 청킹 → 임베딩 → safelaw_statutes
            판례 API → 판례 정규화 → 섹션 청킹   → 임베딩 → safelaw_cases

[질문 시]   사용자 질문 → 로컬 개인정보 마스킹
            → LangGraph retrieve 노드
                 · 프롬프트1 검색어 추출 (법률 검색 문장 + 법률 용어)
                 · (판례 부족 시) 판례 목록 API → 프롬프트2 후보 선별 → 본문 수집 → 증분 색인
                 · 법령·판례 컬렉션 각각 다중 질의 검색 → 재정렬 → 근거 번호 부여
            → LangGraph generate 노드
                 · 프롬프트3 근거 제한 답변(JSON) → 인용 원문 검증 → 최대 3회 교정
            → 화면: 답변 + 인용된 근거 링크 + 쟁점 체크리스트(특화 기능)
```

LangGraph 그래프는 `retrieve → generate` 두 노드의 직선 흐름이다. `python scripts/show_rag_graph.py`로 구조를 출력할 수 있다.

```text
nodes: retrieve, generate
edges: __start__ -> retrieve, retrieve -> generate, generate -> __end__
```

## 2. Vector DB 컬렉션 구조와 메타데이터

두 컬렉션 모두 Chroma `PersistentClient`, cosine 거리, `text-embedding-3-small`(1,536차원)을 쓴다. 문서 종류마다 필요한 메타데이터와 갱신 주기가 다르고, 긴 판례 본문의 유사도 점수가 조문을 밀어내지 않도록 컬렉션을 분리했다.

### 2.1 `safelaw_statutes` — 항목 메타데이터 (RAG 1)

| 필드 | 예시 | 용도 |
|---|---|---|
| `category` | `labor` | 분야 필터 (`where`) |
| `law_id` | `001872:0027001` | 조문 식별, 항목 ID 구성 |
| `law_name` / `article_no` / `article_title` | 근로기준법 / 제27조 / 해고사유 등의 서면통지 | 근거 표시, 인용 조문 일치 검증 |
| `chunk_index` / `chunk_count` | 0 / 1 | 긴 조문 분할 위치 |
| `effective_date` | 2026-10-08 | 시행일 표시 |
| `source_url` | `https://www.law.go.kr/...` | 공식 원문 링크 (law.go.kr HTTPS만 허용) |
| `issue_tags` | 근로계약,해고,... | 임베딩 문맥 보강 |

- 청크 ID: `분야:법령조문ID:순번` (예: `labor:001872:0027001:000`). 고정 ID로 upsert하므로 다시 색인해도 덮어쓰기만 일어난다.
- 항목 색인 텍스트: 조문 본문만 넣으면 "카톡으로 해고" 같은 질문이 잘 걸리지 않아, 도메인·법령명·조문 번호·제목·쟁점 태그·본문을 한 텍스트로 묶었다.

```text
도메인: 근로계약·부당해고
법령: 근로기준법
조문: 제27조 (해고사유 등의 서면통지)
관련 쟁점: 근로계약, 해고, 임금, 근로시간, 직장 내 괴롭힘
본문:
제27조(해고사유 등의 서면통지)
① 사용자는 근로자를 해고하려면 해고사유와 해고시기를 서면으로 통지하여야 한다. ...
```

### 2.2 `safelaw_cases` — 외부 문서 (RAG 2)

| 필드 | 용도 |
|---|---|
| `document_type` = `court_case` | 근거 유형 구분 |
| `category` | 분야 필터 |
| `case_id` / `case_number` / `case_name` | 판례 식별, 사건번호 중복 제거 |
| `court` / `decision_date` / `decision_type` / `case_type` | 근거 표시, 권위 등급 산정 |
| `precedent_level` | 전원합의체·대법원·항소심·기타 |
| `section` / `section_index` | 법적 쟁점·법원의 판단·주문·사실관계 |
| `related_articles` | 판례와 조문(항목)의 연결 |
| `cited_cases` | 참조판례 |
| `source_url` | 공식 판례 원문 링크 |

- 청크 ID: `case:분야:판례ID:섹션:순번`. 여러 질문이 같은 판례를 수집해도 판례 ID와 섹션이 같으면 같은 ID라 서로 덮어쓰지 않고 중복도 생기지 않는다.

## 3. 문서 수집·청킹·색인 흐름

| 단계 | 법령 (RAG 1) | 판례 (RAG 2) |
|---|---|---|
| 수집 | `data/statute_sources.json`의 법령·조문 범위를 현행법령 목록·본문 API로 수집 | 사전: `data/case_sources.json`의 검색어로 판례 목록·본문 API 수집. 질문 시: 법률 용어 상위 3개로 목록 검색 → 프롬프트2 선별 → 선택된 판례만 본문 수집 |
| 정규화 | 조문·항·호·목 구조를 보존한 조문 단위 레코드 | 사건번호·법원·선고일·판시사항·판결요지·참조조문·본문 |
| 청킹 | 조문 단위, 1,200자 초과 조문만 줄 경계 기준으로 분할(중복 최대 150자) | 쟁점·판단·주문·사실관계 섹션 분리 후 1,400자/180자 중복 |
| 색인 | `build_statute_index.py` | `build_case_index.py`, 질문 시 `IncrementalCaseEnricher`가 새 판례만 upsert |
| 재현 | manifest에 건수·SHA-256 기록 | 수집 이력에 질문 SHA-256·검색어·후보별 결정만 기록 (질문 원문 저장 안 함) |

## 4. 검색 결과 병합과 중복 제거

1. **다중 질의 검색**: 원문 질문(가중치 0.7), 재작성 질문(1.3), 법률 용어 각각(1.0)을 임베딩해 컬렉션별로 검색한다.
2. **순위 결합**: 원문·재작성 질의는 가중 RRF(`가중치 / (60 + 순위)`)로 누적하고, 법률 용어는 가장 강한 점수 하나만 더한다. 조문 제목 일치·판례 사건명의 구체 법률어·판례 권위에 작은 가점을 준다.
3. **판례 중복 제거**: 같은 사건번호의 여러 청크는 가장 높은 하나만 남긴다. 구체 쟁점어가 확인되는 판례가 있으면 일반어만 맞은 판례는 제외한다.
4. **근거 번호 부여**: 법령 근거를 먼저 `[근거 1..n]`, 판례를 이어서 번호를 붙인다. 같은 조문의 여러 청크는 한 근거로 합친다. 선택한 조문(채팅)은 검색 순위와 관계없이 `[근거 1]`로 고정하고 검색 결과와 겹치면 한 번만 넣는다.
5. **두 컬렉션의 점수는 직접 비교하지 않는다.** 법령 Top-k와 판례 Top-k를 각각 고른 뒤 근거 목록에서만 합친다.

## 5. 프롬프트

| 프롬프트 | 역할 | 입력 | 출력 형식 | 구현 |
|---|---|---|---|---|
| 프롬프트1 검색어 추출 | 대한민국 생활법률 검색어 변환기. 법률 결론을 판단하지 않고 검색어만 만든다 | 도메인, 마스킹된 질문 | `{"rewritten_query": "...", "legal_terms": ["..."]}` | `LegalQueryExpander` |
| 프롬프트2 후보 선별 (판례) | 공개 판례 수집 리서처. 목록에서 본문을 받을 판례만 고른다 | 도메인, 법률 검색 문장, 법률 용어, `P1..Pn` 판례 목록(사건번호·법원·선고일·판결유형·사건명) | `{"selected": [{"id": "P1", "reason": "..."}]}` | `CaseCandidateSelector` |
| 프롬프트2' 후보 선별 (조문 탐색) | 생활법률 조문 큐레이터. 조건에 직접 해당하는 조문만 고른다 | 도메인, 마스킹된 조건, `C1..Cn` 조문 후보(제목·280자 요약) | `{"selected": [{"id": "C1", "reason": "..."}]}` | `StatuteConditionSearch` |
| 프롬프트3 답변 생성 | 검색 결과 설명 도우미. CONTEXT만 근거로 쓰고, 근거가 없으면 `answerable=false` | 도메인, 마스킹된 질문, CONTEXT(근거 번호·문서 유형·본문) | `{"answerable": true, "summary": {...}, "issues": [...], "favorable_factors": [...], "unfavorable_factors": [...], "additional_facts": [...], "next_steps": [...]}` — 각 주장은 `text`, `citations`, `evidence_quotes` | `build_grounded_answer_messages` |
| 특화 기능 체크리스트 | 판단 요소 3~6개와 상황 대응 표시 | 프롬프트3과 같은 CONTEXT, 마스킹된 상황 | `{"answerable": true, "items": [{"text", "status", "check_question", "citations", "evidence_quotes"}]}` | `IssueChecklistBuilder` |

공통 원칙:

- 모든 프롬프트는 JSON 객체 하나만 출력하게 하고, 코드가 파싱·검증한다.
- CONTEXT·후보 목록·사용자 문장 안의 지시는 데이터로만 취급하라고 명시한다(프롬프트 주입 방어).
- 선별 프롬프트는 후보를 번호로만 보여 주고 번호만 받는다. 목록 밖 번호와 중복은 버리므로 후보에 없는 문서가 선택될 수 없다.
- 판례 선별에는 사용자 질문을 보내지 않고 법률 검색 문장과 용어만 보낸다.
- 선별을 따로 둔 이유: 본문을 받기 전에 버릴 판례를 정해 외부 호출을 줄인다. 실제 실행에서 목록 8건 중 1건만 골라 본문 조회가 8회에서 1회로 줄었다.

## 6. 청크 크기·중복 길이·Top-k

모든 값은 `.env`(`STATUTE_CHUNK_SIZE`, `STATUTE_CHUNK_OVERLAP`, `CASE_CHUNK_SIZE`, `CASE_CHUNK_OVERLAP`, `RAG_TOP_K`)로 조정한다.

| 설정 | 값 | 선택 이유 |
|---|---|---|
| 법령 청크 | 1,200자 / 중복 150자 | 조문 하나가 한 청크에 온전히 남는 크기다. 381조문 중 5개만 2개로 나뉜다. 항·호 경계에서 자르므로 중복은 경계가 맞지 않을 때만 쓴다. |
| 판례 청크 | 1,400자 / 중복 180자 | 판례의 판단 문단이 길어 법령보다 크게 잡고, 섹션 경계를 넘는 문장을 보존하려고 중복을 둔다. |
| Top-k | 5 | 핵심 조문(제27조)은 Top-k 3부터 들어오지만 검색어 변환 결과가 실행마다 달라 여유를 두었다. 8로 늘리면 관련 약한 조문의 비중이 커진다. |

| 법령 | 800 / 150 | 401 |
| 법령 | 500 / 100 | 436 |

## 7. 근거 표시 방식

1. 프롬프트3이 주장마다 `citations`와 CONTEXT에서 그대로 복사한 8자 이상의 `evidence_quotes`를 낸다.
2. 코드가 검증한다: 근거 번호가 실제 검색 결과에 있는지, 인용 문구가 그 원문에 있는지(공백 무시), 본문에서 언급한 조문 번호가 인용한 조문과 일치하는지, 출처가 law.go.kr HTTPS인지, 본문에 URL이 없는지.
3. 실패하면 실패 이유를 붙여 다시 생성하고, 마지막 3차 시도는 가장 직접적인 근거 하나와 요약만 요구한다. 세 번 모두 실패하면 모델 문장을 버리고 고정 차단 문구를 보여 준다.
4. 통과한 답변은 코드가 Markdown으로 렌더링하고, **실제로 인용된 근거만** `확인된 근거` 목록과 `근거 링크만 모아보기`에 제목·공식 링크로 표시한다. 법령 근거와 유사 판례를 나눠 보여 준다.
5. 근거가 없거나(`no_evidence`), 근거로 답할 수 없거나(`insufficient_evidence`), 인용 검증에 실패하면(`invalid_citations`) 그 사실을 상태 문구로 안내한다.

## 8. 도메인 특화 기능 설계 이유

**내 상황 쟁점 체크리스트**를 특화 기능으로 정했다. 법률 상담 사용자에게 필요한 것은 결론 예측이 아니라 "법이 무엇을 따지는지"와 "내 사실관계에서 무엇을 확인해야 하는지"이기 때문이다.

- 답변과 같은 근거를 재사용해 판단 요소를 뽑고, 각 요소가 상황 문장에 `✅ 나와 있음`·`⚠️ 다름`·`❓ 확인 필요` 중 어디에 해당하는지만 표시한다. 요건 충족이나 승소 여부는 판단하지 않는다.
- 항목마다 확인 질문을 체크박스로 주어 사용자가 직접 사실을 확인하게 한다.
- 모든 항목은 답변과 같은 인용 검증을 거친다. 항목은 서로 독립적이므로 검증에 실패한 항목만 빼고, 뺀 개수를 화면에 표시한다.

조건 기반 탐색(F2011)과 조문별 채팅(F2009)은 "조문"을 항목으로 보는 설계에서 나왔다. 사용자가 상황을 잘 설명하지 못해도 "해고 통보 절차를 정한 조문"처럼 조건으로 조문을 먼저 찾고, 그 조문을 고정 근거로 둔 채 질문을 이어갈 수 있다.

## 9. 선택 이유, 겪은 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| "카톡으로 나오지 말래요"로 제27조가 Top-5 밖 | 일상어와 법률 용어의 차이 | 규칙+LLM 검색어 변환(프롬프트1), 원문·재작성·법률 용어 다중 질의 |
| 법률 용어 점수를 단순 누적하자 Recall은 올랐지만 MRR 하락 (0.525 → 0.411) | 후보 확장과 순위 결정이 섞임 | 후보 수집과 재정렬 분리, 용어는 가장 강한 점수만 반영 → Recall@5 1.000, MRR 0.781 |
| 판례 오염률 0.67 | 본문검색이 주변적으로만 관련된 판례를 섞음 | 사건명·참조조문 하이브리드 재정렬, 구체 쟁점어 필터 → 오염률 0.53 |
| 답변 인용 검증 실패로 성공률 41.7% | 모델이 원문을 조금씩 바꿔 인용 | 실패 이유를 붙인 재생성, 3차 시도는 근거 하나만 요구 → 답변 성공률 75.0%, 인용 정확성 100% 유지 |
| 판례를 모두 받아 거르면 본문 API 호출이 많음 | 수집 후 필터 | 프롬프트2 후보 선별로 본문 조회 전 탈락 |
| 체크리스트 1개 항목 인용 오류로 전체 차단 | 전부 아니면 전무 검증 | 항목 단위 검증, 뺀 개수 표시 |
| 새 탭 추가 후 사용자 지정 마스킹 단어 누락 | 입력 경로마다 마스킹 옵션이 달랐음 | 두 탭 모든 외부 호출 경로에 같은 마스킹 옵션 적용 |

세부 기록은 [`troubleshooting.md`](troubleshooting.md), [`search-quality.md`](search-quality.md), [`case-retrieval-evaluation.md`](case-retrieval-evaluation.md), [`end-to-end-rag-evaluation.md`](end-to-end-rag-evaluation.md)에 있다.
