# 모델 역할 분리 전략

한 요청에 모든 작업을 같은 채팅 모델로 처리할 필요는 없다. SafeLaw는 비용·속도·정확도와 개인정보 경계를 기준으로 모델 역할을 나눈다.

| 단계 | 권장 모델/방식 | 이유 |
|---|---|---|
| 개인정보 마스킹 | 로컬 정규식·규칙 | 원문 식별정보를 외부 모델로 보내지 않기 위해 모델을 사용하지 않는다. |
| 도메인 분류·검색어 변환 | 빠르고 저렴한 채팅 모델 | 짧은 JSON과 법률 검색어만 만들므로 큰 생성 모델이 항상 필요하지 않다. |
| 문서·질문 임베딩 | 동일한 임베딩 모델 | 같은 Chroma 컬렉션 안의 문서와 질문은 같은 벡터 공간·차원이어야 한다. |
| 최종 근거 답변 | 더 강한 채팅 모델 | 여러 법령·판례를 구분하고 인용 JSON 형식을 지키는 능력이 중요하다. |
| 인용문 검증 | 로컬 결정적 코드 | 모델 스스로 자기 답변을 채점하게 하지 않고 실제 원문 포함 여부를 검사한다. |
| 오프라인 평가·오류 분석 | 선택적으로 별도 평가 모델 + 사람 검토 | 운영 응답과 독립된 관점으로 실패 유형을 분류하되 최종 정답표는 사람이 확인한다. |

환경변수는 다음처럼 역할별로 지정할 수 있다. GMS에서 실제 사용 가능한 모델 이름을 넣어야 한다. 검색 모델과 답변 모델을 비우면 둘 다 `gpt-5.4-mini`를 사용한다.

```dotenv
GMS_QUERY_MODEL=gpt-5.4-mini
GMS_ANSWER_MODEL=gpt-5.4-mini
GMS_EMBEDDING_MODEL=text-embedding-3-small
```

예를 들어 검색어 변환에는 빠른 모델, 최종 답변에는 지시 준수와 구조화 출력이 더 안정적인 모델을 배치할 수 있다. 반면 동일 컬렉션의 문서 색인에는 A 임베딩 모델, 질문에는 B 임베딩 모델을 쓰면 안 된다. 법령과 판례에 서로 다른 임베딩 모델을 쓰는 것도 기술적으로 가능하지만 두 검색 점수를 그대로 비교할 수 없으므로, 현재는 두 컬렉션 모두 같은 모델을 사용하고 결과 목록만 분리한다.

실제 통합 테스트에서 `gpt-5-nano`는 법령과 판례를 적절히 찾고도 JSON 괄호를 잘못 생성해 인용 검증에서 차단됐다. 따라서 짧은 검색어 JSON은 nano가 담당하고, 여러 근거를 묶는 최종 답변 JSON은 `gpt-5.4-mini`가 담당하도록 기본 라우팅을 정했다.

## 2026-10-22 검색어 변환 모델 변경

질문 하나에 31.8~64.0초가 걸려 구간별로 측정하니, 답변 생성은 4~5초인데 검색이 22~29초였고 그 대부분이 `gpt-5-nano` 검색어 변환(호출당 26~34초, 3번 중 1번 HTTP 오류)이었다. 같은 프롬프트로 비교한 결과는 다음과 같다.

| 검색어 변환 모델 | 호출당 시간 | 검색어 품질 |
|---|---|---|
| `gpt-5-nano` | 26~30초 | 법률 용어 8개 내외 |
| `gpt-5-nano` + `reasoning_effort=minimal` | 1.7~6.4초 | "구인·고용노동관계법", "법정대리인" 등 잡음이 많음 |
| `gpt-5.4-mini` | 대부분 1.1~1.3초 | 대항력·우선변제권 등 핵심 용어, 5~7개 |

기본값을 `gpt-5.4-mini`로 바꿔 전체 처리 시간이 8.3~16.7초로 줄었다. 대신 용어 수가 줄어 법령 MRR이 0.781 → 0.740, E2E 답변 성공률이 0.750 → 0.667로 낮아졌다. 속도보다 검색 품질을 우선할 때는 `GMS_QUERY_MODEL=gpt-5-nano`로 되돌린다.
